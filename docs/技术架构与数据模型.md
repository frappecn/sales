# 技术架构与数据模型

## 1. 总体架构
采用模块化单体：Frappe Framework + ERPNext + Sales App。首期不拆分微服务，降低部署、运维和数据一致性成本。

## 2. 扩展原则
优先使用 Frappe DocType、Controller、Hooks、标准 API、权限机制、Patch、Background Jobs 和 Scheduler。仅在官方机制无法满足且经过评估时才考虑特殊扩展。

## 3. 模块边界
Sales 计划包含：
- 组织与履约网点扩展
- 消费者商城接口
- OMS 订单编排
- WMS 仓内作业
- 库存预占与可售量
- 区域商品与价格
- 配送任务与轨迹
- 售后服务
- 运营配置与经营分析

ERPNext 优先承担：
- Item、Customer、Supplier 等主数据
- Selling、Buying 等标准单据
- Warehouse、Stock Entry、Purchase Receipt、Delivery Note 等库存流程
- Accounts、Payment Entry、Journal Entry 等财务流程

## 4. 组织与仓库模型
- Company：法律/会计主体，不等同于每个门店。
- Region：业务区域，可作为 Sales 扩展 DocType。
- Branch：门店或前置仓业务网点，可作为 Sales 扩展 DocType。
- Warehouse：ERPNext 实际库存仓库。
- 一个 Branch 可关联一个或多个 Warehouse，具体关系按业务确认。
- 多企业 SaaS 隔离方案尚未确定；不得将单站点多 Company 与多租户隔离混为一谈。

## 5. 核心数据原则
- 订单状态与支付状态分离。
- 库存预占与真实库存分离；预占应有生命周期、释放机制和审计记录。
- 库存账本以 ERPNext 为准，避免双账本。
- 财务总账通过 ERPNext 标准业务流程生成，不由 Sales 直接写 GL Entry。
- 订单、支付、库存、配送之间通过明确关联键追踪。
- 对外请求使用幂等键；关键状态变更需考虑事务边界与并发控制。

## 6. 前端策略
第一阶段优先响应式 Web。消费者商城和仓内高频操作界面可按体验需要独立建设前端，通过 Frappe 标准 API 集成。是否采用 PWA、独立移动端或离线能力待评估。

## 7. 运行环境
Python、Node.js、数据库、Redis、Frappe、ERPNext 版本必须与选定官方兼容版本一致。生产环境锁定依赖版本和 Commit SHA，不直接追随未经验证的 develop 最新代码。
