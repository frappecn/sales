# 上游更新与发布规范

## 1. 上游关系
- Frappe 上游：frappe/frappe。
- ERPNext 上游：frappe/erpnext。
- 组织 Fork：frappecn/frappe、frappecn/erpnext。
- 自主应用：frappecn/sales。

## 2. 基线原则
选择经过评估的 Frappe 与 ERPNext 兼容版本作为项目基线。记录上游仓库、分支、Commit SHA、Python/Node/数据库等依赖版本。不得仅凭分支名称推断兼容性。

## 3. 更新策略
安全修复优先；重要缺陷其次；性能与新功能按业务价值评估。每次更新记录上游原始 Commit、自主 Fork 的处理 Commit、移植内容、冲突、测试结果和未移植原因。

## 4. 更新流程
检查上游 → 评估依赖和变更 → 在隔离分支同步 → 解决冲突 → 执行自动化测试 → 部署测试环境 → 验收 → 合并发布。禁止直接将未经验证的上游 develop 推入生产。

## 5. 核心修改
默认不修改 Frappe / ERPNext 核心。确需修改时，必须记录修改文件、原因、上游差异、升级影响和专项测试，并优先评估能否改为 Sales App 扩展。

## 6. 发布与回滚
发布前备份数据库和文件，锁定全部 Commit SHA，验证迁移脚本和关键业务流程。回滚方案必须区分代码回滚与数据库恢复；不可逆 Patch 不得假设可通过回退代码恢复。
